# Урок 22. Робот целиком: рулим и видим угол (Этап 3. Робот)

Объединяем **урок 20** (угол наклона с MPU6050) и **урок 21** (моторы через TB6612FNG)
в одну прошивку. Раньше это были два разных скетча и два разных запуска; теперь ESP32
одновременно **слушает команды** и **шлёт телеметрию** — в дашборде мы жмём стрелки и в
ту же секунду видим, как машинка кренится.

```
Браузер --HTTP--> ASP.NET --AMQP--> RabbitMQ --MQTT(1883)--> ESP32 --> TB6612FNG --> моторы
Браузер <--SignalR-- ASP.NET <--AMQP-- RabbitMQ <--MQTT----- ESP32 <-- MPU6050 (pitch/roll/yaw)
```

Бэкенд лежит в `C:\Projects\arduino\ArduinoEducation` (проект TelemetryApi).

## Что изучаем

| Понятие                     | Где в коде                                                        |
|-----------------------------|-------------------------------------------------------------------|
| **дуплекс на одном клиенте**| `mqtt.subscribe(TOPIC_DRIVE)` + `mqtt.publish(TOPIC_PITCH, …)`     |
| **неблокирующий loop**      | `mqtt.loop()` каждый проход, publish по `millis()`, без `delay`    |
| **частый опрос датчика**    | `mpu.update()` в каждом `loop()`, publish раз в 200 мс             |
| **обратная связь**          | `updateTiltGuard()` — датчик сам глушит моторы                     |
| **гистерезис**              | `TILT_LIMIT` 45° на вход, `TILT_RELEASE` 35° на выход              |
| **доверие к сэмплу**        | угол берём только когда \|a\| ≈ 1 g — на рывке акселерометр врёт     |
| **дебаунс**                 | взводимся, если наклон держится `TILT_DEBOUNCE_MS` 300 мс          |
| **publish on change**       | `publishGuardIfChanged()` — метрика `guard` шлётся только при смене|

## Почему это не просто «два файла в один»

### 1. Один MQTT-клиент на два направления

`PubSubClient` однопоточный: и приём подписок, и отправка идут через `mqtt.loop()`.
Если где-то в `loop()` появится `delay(200)`, команда `stop` приедет с опозданием —
робот проедет лишние сантиметры. Поэтому в уроке 22 **весь** `loop()` неблокирующий:
публикация по таймеру `millis()`, единственный `delay` остался в `reconnect()`
(там мы всё равно ничего не можем делать — и моторы там на всякий случай глушим).

### 2. Датчик опрашиваем чаще, чем публикуем

В уроке 20 `mpu.update()` вызывался раз в 200 мс — вместе с публикацией. Но `tockn`
считает `yaw` как **интеграл гироскопа по времени** внутри `update()`: чем реже его
дёргаешь, тем грубее интеграл и тем быстрее уплывает курс. В уроке 22 разделили:

```cpp
mpu.update();                       // каждую итерацию loop() — точнее yaw
if (now - lastPublish >= 200) { …publish…; }   // в сеть — 5 раз в секунду
```

### 3. Защита по наклону (tilt guard)

Вот ради чего уроки и объединяются: **датчик может влиять на моторы**. Если робот
задрался круче `TILT_LIMIT` (наехал на препятствие, встал на попа, свисает со стола),
прошивка сама глушит моторы и игнорирует команды движения:

```cpp
if (fabsf(accelG - 1.0f) > ACCEL_TRUST_BAND) return;   // сэмплу не верим

float tilt = max(fabsf(pitch), fabsf(roll));
if (!tiltBlocked) {
  if (tilt >= TILT_LIMIT) {
    if (overLimitSince == 0) overLimitSince = millis();
    if (millis() - overLimitSince >= TILT_DEBOUNCE_MS) { tiltBlocked = true; driveStop(); }
  } else overLimitSince = 0;
} else if (tilt <= TILT_RELEASE) { tiltBlocked = false; }
```

Два разных порога — это **гистерезис**. С одним порогом на границе 45.0° значение
дёргалось бы туда-сюда и защита включалась/выключалась несколько раз в секунду.
Команда `stop` исполняется **всегда**, даже при активной защите: стоп безопасен.

#### Почему одного порога мало: защита глушила сама себя

Наивная версия (просто `tilt >= TILT_LIMIT`) срабатывала на **каждом старте моторов**.
В мониторе это выглядело так:

```
[MQTT] -> sensors/esp32/pitch = 1.8      <- робот стоит ровно, 2 градуса
[MQTT] <- commands/esp32/drive = forward <- команда пришла
[GUARD] наклон 47 град >= 45 — СТОП      <- и через миг «наклон» 47 градусов
[GUARD] наклон 28 град <= 35 — снова можно ехать
```

Причина не в датчике и не в креплении. `pitch`/`roll` считаются из **вектора
ускорения**, а акселерометр меряет гравитацию **плюс** ускорение самого робота.
Пока машинка стоит, это одно и то же, и `atan2` даёт честный угол. На пусковом рывке
добавляется горизонтальная составляющая — и тот же `atan2` рисует 45–48° на ровном
полу. Моторы глохли, робот дёргался и стоял на месте. Вес камеры из урока 26 сделал
кивки резче и превратил это из редкости в постоянство.

Отсюда два фильтра, и оба нужны:

1. **Доверие к сэмплу.** В покое \|a\| = 1 g. Если модуль ускорения уехал больше чем на
   `ACCEL_TRUST_BAND` (0.25 g), робот разгоняется, тормозит или подпрыгивает — угол из
   такого сэмпла мусор. Такой сэмпл **пропускается целиком**: он не взводит защиту, но
   и не снимает её и не сбрасывает отсчёт.
2. **Дебаунс.** Взводимся, только если наклон держится за порогом непрерывно
   `TILT_DEBOUNCE_MS` (300 мс). Настоящий переворот держит наклон секундами; замеренные
   ложные срабатывания жили 47–228 мс — то есть все короче 300.

По отдельности каждый слабее: проверка \|a\| не спасёт от долгой тряски, а дебаунс без
неё просто дождётся конца рывка вместо того, чтобы не считать его вовсе. **Снятие**
защиты дебаунса не имеет — по первому достоверному сэмплу ниже `TILT_RELEASE`: держать
робота заблокированным дольше нужного хуже, чем отпустить раньше.

После разблокировки моторы сами не заводятся — ждём следующую команду. Браузер, пока
кнопка зажата, повторяет её каждые ~300 мс, так что для пользователя это выглядит как
«отпустило и поехали дальше».

### 4. `guard` — метрика, которую шлём событием, а не таймером

Состояние защиты уходит в бэкенд как **обычная метрика** `sensors/esp32/guard` со
значением `0`/`1`. Бэкенд менять не надо — это то же «голое число», что и `pitch`.
Но публикуем её **только при изменении**:

```
publish by timer   → 5 одинаковых строк в секунду в PostgreSQL (мусор)
publish on change  → одна строка на событие
```

Углы — это поток измерений (шлём по таймеру), защита — событие (шлём по факту).
После реконнекта `guardSent` сбрасывается в `-1`, чтобы заново сообщить состояние:
бэкенд мог пропустить событие, пока связи не было.

## Подключение

Главное отличие от уроков 20 и 21: здесь **датчик и драйвер моторов подключены
одновременно**, поэтому их пины не имеют права пересекаться. Актуальная карта —
`include/pins.h`:

| Устройство       | Сигнал | ESP32                    |
|------------------|--------|--------------------------|
| MPU6050 (GY-521) | VCC    | 3V3                      |
|                  | GND    | GND                      |
|                  | SDA    | GPIO32 (`MPU_SDA`)       |
|                  | SCL    | GPIO17 (`MPU_SCL`)       |
| TB6612FNG, мотор A (левый) | AIN1 | GPIO13 (`MOTOR_AIN1`, orange) |
|                  | AIN2   | GPIO14 (`MOTOR_AIN2`, yellow) |
|                  | PWMA   | GPIO25 (`MOTOR_PWMA`, green)  |
| TB6612FNG, мотор B (правый)| BIN1 | GPIO26 (`MOTOR_BIN1`, brown)  |
|                  | BIN2   | GPIO27 (`MOTOR_BIN2`, violet) |
|                  | PWMB   | GPIO33 (`MOTOR_PWMB`, white)  |
| TB6612FNG        | STBY   | 3V3 (всегда включён)     |
|                  | VM     | питание моторов (батарея)|
|                  | VCC    | 3V3                      |
|                  | GND    | GND (общая с ESP32!)     |

> `MPU_SCL` и `MOTOR_PWMB` когда-то были наоборот (17 под ШИМ, 33 под SCL) — при
> отладке `lesson_check_tb6612` их поменяли местами. Ориентируйся на `pins.h`, а не
> на старые скриншоты.

> **Питание.** Моторы от USB-шины ESP32 не питай: просадка на старте роняет контроллер
> (`Brownout detector was triggered` в мониторе). Отдельная батарея на `VM`, **общая
> земля** и электролит 100–470 мкФ по питанию драйвера снимают 90% «мистических»
> перезагрузок и зависаний I2C.

## Настройка перед прошивкой

В `lesson22_robot_telemetry.cpp`:

1. `SSID` / `PASS` — Wi-Fi (ESP32 и ПК в одной сети).
2. `MQTT_BROKER` — **LAN-IP компьютера** с docker (`ipconfig` → IPv4), не `localhost`.
3. `MQTT_USER` / `MQTT_PASS` — пользователь RabbitMQ (`esp` / `esp-pass`; `guest`
   работает только с localhost).
4. `SPEED` (0..255) — скорость; `TILT_LIMIT` / `TILT_RELEASE` — пороги защиты;
   `FAILSAFE_MS` 700 мс — должно быть больше периода повтора команд из браузера (~300 мс).

## Запуск

```bash
# 1) бэкенд (в папке ArduinoEducation)
docker compose up -d          # RabbitMQ + PostgreSQL
dotnet run                    # API + консьюмер + SignalR

# 2) дашборд
cd dashboard && npm run dev   # http://localhost:5173

# 3) прошивка урока (робот стоит РОВНО и НЕПОДВИЖНО первые ~3 секунды — калибровка)
pio run -e lesson22_robot_telemetry -t upload
pio device monitor            # 115200
```

Порядок важен только для калибровки: пока в мониторе идёт `калибровка гироскопа`,
робота не трогаем — иначе `yaw` уплывёт с первой секунды.

## Проверка end-to-end

- В мониторе одновременно видно оба направления:
  `[MQTT] -> sensors/esp32/pitch = -2.1` и `[MQTT] <- commands/esp32/drive = forward`.
- Жмём стрелку в дашборде — робот едет, гейджи pitch/roll и 3D-модель шевелятся.
- Наклоняем робота круче 45° — в мониторе `[GUARD] … СТОП`, моторы глохнут, в
  дашборде появляется бейдж **TILT GUARD**, стрелки перестают действовать.
- Ставим ровно — `[GUARD] … снова можно ехать`, бейдж гаснет, управление вернулось.
- Закрываем вкладку на ходу — через 700 мс `[DRIVE] failsafe: команд нет, стоп`.
- `GET http://localhost:54344/api/telemetry/latest?device=esp32` — в БД лежат
  `pitch`/`roll`/`yaw` и редкие строки `guard`.

## Если что-то не так

| Симптом                                          | Причина                                                         |
|--------------------------------------------------|-----------------------------------------------------------------|
| Углы «залипли» после первой поездки              | I2C повис от помех моторов — общая земля, конденсатор, короткие провода к датчику |
| `Brownout detector was triggered` при старте     | Моторы питаются от USB — отдельная батарея на `VM`               |
| Команды приходят с задержкой                     | В `loop()` попал `delay` / долгая печать в Serial               |
| `yaw` бешено крутится на ходу                    | Так и есть: гиро-only дрейфует от вибрации. Нужен магнитометр/фильтр |
| Защита срабатывает на ровном месте, при старте   | Так было до фильтров: рывок моторов врёт акселерометру. Если вернулось — подними `TILT_DEBOUNCE_MS` или сузь `ACCEL_TRUST_BAND` (см. раздел 3) |
| Защита не срабатывает при реальном перевороте    | `TILT_DEBOUNCE_MS` слишком велик, либо робот трясёт так, что \|a\| постоянно вне полосы доверия — расширь `ACCEL_TRUST_BAND` |
| Датчик закреплён под наклоном                    | Углы смещены на постоянную величину — выровняй крепление (фильтры от этого не спасают) |
| Мотор крутится не туда                           | Поменяй местами два провода этого мотора (или знаки `dir`)       |
