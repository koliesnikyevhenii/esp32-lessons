# Урок 24. Видеопоток MJPEG (Этап 6. Камера)

Урок 23 дал фотоаппарат. Здесь получаем **видео** — и без единой строчки видеокодека.

```
Браузер --GET :81/stream--> ESP32-S3-CAM ...кадр...кадр...кадр...  (ответ не закрывается)
```

## Что изучаем

| Понятие | Где в коде |
|---|---|
| **MJPEG** | `multipart/x-mixed-replace;boundary=...` |
| **chunked-ответ** | `httpd_resp_send_chunk()` в бесконечном `while` |
| **esp_http_server** | вместо `WebServer` — работает в своих задачах FreeRTOS |
| **два сервера** | `:80` страница и кнопки, `:81` поток |
| **свежесть кадра** | `grab_mode = CAMERA_GRAB_LATEST` |
| **цена разрешения** | к/с и кбит/с на QVGA / VGA / SVGA / UXGA |

## Что такое MJPEG

MJPEG (Motion JPEG) — это **не кодек**, а соглашение: «шлю подряд обычные JPEG-кадры».
Никакого сжатия между кадрами (как в H.264) нет, поэтому:

- **плюс:** кодировать умеет сам сенсор, декодировать — любой браузер, задержка
  минимальная (нет буфера предсказаний), потеря кадра ничего не портит;
- **минус:** битрейт в разы больше H.264 при том же качестве.

Для FPV-машинки в локальной сети это идеальный компромисс — и ровно поэтому все
камеры видеонаблюдения умеют MJPEG.

Технически поток — это **один HTTP-ответ**, который никогда не заканчивается:

```
HTTP/1.1 200 OK
Content-Type: multipart/x-mixed-replace;boundary=esp32camframe

--esp32camframe
Content-Type: image/jpeg
Content-Length: 24118

<24118 байт JPEG>
--esp32camframe
Content-Type: image/jpeg
Content-Length: 23904

<23904 байт JPEG>
...
```

`x-mixed-replace` — это буквально «заменяй предыдущую часть следующей». Браузер
показывает такое прямо в `<img src="...">`, без JS.

## Почему `WebServer` из уроков 17 и 23 больше не годится

`WebServer` **синхронный**: он обрабатывает запросы внутри `server.handleClient()`,
то есть внутри `loop()`. А обработчик стрима не возвращается никогда — он крутит
бесконечный цикл. Итог: `loop()` заблокирован навсегда, ни MQTT, ни таймеры, ни
другие запросы не работают.

`esp_http_server` (тот же, что в примере CameraWebServer) поднимает **свои задачи
FreeRTOS**. Поэтому в уроке 24 `loop()` пустой — и в уроке 26 мы спокойно займём
его MQTT-клиентом.

## Почему ДВА сервера на двух портах

У httpd ограниченное число воркеров. Пока один занят бесконечным стримом, обычные
запросы (`/stats`, `/size`) на **этот же** сервер встают в очередь и страница
подвисает. Решение — как в официальном примере: страница на `:80`, поток на `:81`.

```cpp
httpd_config_t stream = HTTPD_DEFAULT_CONFIG();
stream.server_port = 81;
stream.ctrl_port   = 32769;   // ОБЯЗАТЕЛЬНО другой!
```

`ctrl_port` — внутренний UDP-порт управления httpd. Если оставить у двух серверов
одинаковый, второй `httpd_start()` просто не поднимется. Это неочевидная грабля.

Из-за двух портов адрес стрима собирается в браузере:

```js
cam.src = 'http://' + location.hostname + ':81/stream?t=' + Date.now();
```

## Один кадр = три чанка

```cpp
httpd_resp_send_chunk(req, STREAM_BOUNDARY, ...);   // "\r\n--boundary\r\n"
httpd_resp_send_chunk(req, partBuf, hlen);          // Content-Type + Content-Length
httpd_resp_send_chunk(req, fb->buf, fb->len);       // сам JPEG
esp_camera_fb_return(fb);                           // сразу вернуть буфер
if (res != ESP_OK) break;                           // клиент закрыл вкладку
```

Ошибка отправки — это и есть «клиент ушёл»: других способов узнать нет.

## `CAMERA_GRAB_LATEST` против `CAMERA_GRAB_WHEN_EMPTY`

При `fb_count = 2` драйвер держит очередь кадров. `WHEN_EMPTY` отдаёт **самый старый
готовый** — картинка отстаёт от реальности на `fb_count` кадров. Для видеонаблюдения
неважно, для FPV смертельно: рулишь по вчерашней картинке. `LATEST` всегда отдаёт
свежий, лишние выбрасывает.

## Сколько к/с ждать

Страница раз в секунду читает `/stats`, а считает статистику сам стрим-обработчик.
Порядок величин для ESP32-S3 при нормальном сигнале (−50…−60 dBm). Точные цифры
меряй сам — они в `/stats`; у S3 они заметно выше, чем у классического ESP32, потому
что у него отдельный блок LCD_CAM под параллельную шину камеры:

| Разрешение | к/с | битрейт |
|---|---|---|
| QVGA 320×240 | 25 и выше | ~1 Мбит/с |
| VGA 640×480 | 18–25 | 4–6 Мбит/с |
| SVGA 800×600 | 15–20 | 5–7 Мбит/с |
| UXGA 1600×1200 | 5–10 | 6–9 Мбит/с |

Узкое место — **не сенсор, а Wi-Fi**. Проверить легко: отойди с телефоном подальше,
`RSSI` упадёт, к/с просядут при том же разрешении. Поэтому в `setup()` стоит
`WiFi.setSleep(false)` — со включённым power save к/с падают в разы.

## Эндпоинты

| URL | Что делает |
|---|---|
| `:80/` | страница: `<img>` со стримом, кнопки разрешения, вспышка, статистика |
| `:80/stats` | JSON `{fps, kbps, clients, rssi, heap}` |
| `:80/size?v=N` | разрешение: 5=QVGA, 8=VGA, 9=SVGA, 13=UXGA |
| `:80/flash?v=0..255` | вспышка |
| `:81/stream` | сам MJPEG-поток |

После смены разрешения поток переоткрывается (`fetch('/size').then(open_)`) — иначе
`<img>` продолжает жевать старый ответ и залипает.

## Запуск

```bash
pio run -e lesson24_cam_stream -t upload

```

## Что проверить глазами

1. Видео живое, задержка «на глаз» — 0.1–0.3 с (помаши рукой).
2. Переключай разрешение и смотри, как меняются к/с и кбит/с. Найди своё рабочее
   разрешение — то, где картинка ещё приемлема, а к/с ещё держатся.
3. Открой стрим **во второй вкладке**: `clients: 2`, но к/с в каждой упадут почти
   вдвое — сенсор и Wi-Fi одни на всех.
4. Закрой вкладку — в мониторе появится «клиент отключился». Так httpd узнаёт об уходе.
5. Отойди от роутера, посмотри на `RSSI` и к/с.
6. Покрути объектив, поймай фокус на живой картинке.
