# Урок 26. FPV-машинка (Этап 6. Камера)

Капстоун Этапа 6. Открываешь одну страницу — видишь картинку «из глаз робота» и
рулишь им, глядя в эту картинку. FPV = First Person View, ровно как на дронах.

```
Браузер ──GET :81/stream──> ESP32-S3-CAM ──── видео
        ──GET /drive?cmd=─> ESP32-S3-CAM ──MQTT──> RabbitMQ ──MQTT──> ESP32 DevKit
                                                                    └─> TB6612FNG ─> моторы
                                          RabbitMQ <──MQTT── DevKit (pitch/roll/yaw/guard)
                                              │
                                        AMQP ─┴─> .NET Worker ─> PostgreSQL ─> дашборд
```

## Архитектура: плат ДВЕ, и это осознанное решение

ESP32-S3-CAM **не крутит моторы**. Она делает две вещи:

1. отдаёт MJPEG-поток (урок 24);
2. **перепубликовывает** нажатия кнопок в топик `commands/esp32/drive` — тот самый,
   который урок 22 уже слушает.

Что из этого следует:

- прошивку робота (урок 22) менять **не надо** — контракт топиков не изменился;
- бэкенд и React-дашборд менять **не надо**;
- рулить можно и из дашборда, и из FPV-страницы — **хоть одновременно**, робот
  слушает топик, а не конкретного клиента. Это и есть смысл шины сообщений.

Почему не «всё на одной плате»: на ESP32-S3 свободных пинов как раз хватает и на
драйвер моторов, и на IMU — то есть технически вариант «камера сама рулит» здесь
возможен (на старой AI-Thinker он был почти нереален). Но на DevKit **уже** разведены
моторы и MPU6050 и работает защита по наклону из урока 22 — переносить всё это на
камеру значит выбросить готовое и заново возиться с проводкой. Вариант B ниже — для
тех, кому важнее одна плата, чем сохранность урока 22.

## Что изучаем

| Понятие | Где в коде |
|---|---|
| **две задачи, один MQTT-клиент** | `xQueueSend()` в HTTP-обработчике → `xQueueReceive()` + `publish` в `loop()` |
| **камера как MQTT-устройство** | publish `sensors/esp32cam/fps\|rssi`, subscribe `sensors/esp32/guard` |
| **`<device>` — не константа проекта** | у камеры свой device-id `esp32cam` |
| **повтор команды** | страница шлёт команду каждые 300 мс, робот глушится через 700 мс |
| **аллоу-лист** | `isAllowed()` — те же 5 слов, что на бэкенде и в прошивке робота |
| **202 вместо 200** | «команда принята», а не «робот поехал» |

## Почему нельзя публиковать прямо из HTTP-обработчика

`/drive` исполняется в задаче `esp_http_server`, а `PubSubClient` **не
потокобезопасен**: у него один буфер на приём и отправку. Publish из двух задач
одновременно — это порванные пакеты и отвал соединения, причём плавающий и
невоспроизводимый.

Классическое решение — очередь:

```cpp
typedef struct { char text[12]; } cmd_msg_t;
QueueHandle_t cmdQueue = xQueueCreate(8, sizeof(cmd_msg_t));

// HTTP-задача (producer):
xQueueSend(cmdQueue, &msg, 0);          // таймаут 0: лучше выбросить, чем задержать стрим

// loop() (consumer):
while (xQueueReceive(cmdQueue, &msg, 0) == pdTRUE) mqtt.publish(TOPIC_DRIVE, msg.text);
```

Публикует **только `loop()`** — один поток, один клиент. Это первый случай в курсе,
где реально видно, что ESP32 — двухъядерная многозадачная система, а не «большой
Arduino».

## Повтор команды и failsafe

В уроке 21 у робота стоит failsafe: **нет команд 700 мс → моторы стоп**. Поэтому
пульт обязан «подтверждать» удержание кнопки:

```js
const REPEAT = 300;                    // мс
start(c) { send(c); timer = setInterval(() => send(c), REPEAT); }
release() { clearInterval(timer); send('stop'); }
```

Плюс `addEventListener('blur', release)` — ушёл со страницы с зажатой кнопкой, робот
не должен уехать. Три независимых предохранителя: `stop` на отпускание, failsafe по
таймеру, tilt guard по наклону. Для машинки с моторами это не паранойя.

## Обратная связь: камера слушает робота

Камера подписана на `sensors/esp32/guard` — метрику tilt guard из урока 22. Если
робот задрался и заблокировал сам себя, на FPV-странице появляется красная строка
«РОБОТ ЗАБЛОКИРОВАН ПО НАКЛОНУ». Кнопки при этом продолжают работать — команды
уезжают в брокер, но робот их игнорирует.

Это ровно то, что записано в бэкенде: **202 ≠ «робот поехал»**. Устройство — хозяин
ситуации, а пульт лишь просит.

## Своя телеметрия камеры

Раз в 2 секунды камера публикует `sensors/esp32cam/fps` и `sensors/esp32cam/rssi` —
голые числа, тот же конвейер, что у робота. Бэкенд менять не пришлось: `device` он
разбирает из routing key.

Где смотреть:

```
GET /api/telemetry/devices                      -> появится "esp32cam"
GET /api/telemetry/latest?device=esp32cam        -> fps и rssi
```

В React-дашборде их **не видно**: он фильтрует по `device` и списку метрик
(`pitch`/`roll`/`yaw`/`guard`). Это нормально — данные в БД есть, история строится.

## Настройка перед прошивкой

В `lesson26_fpv_robot.cpp`:

1. `SSID` / `PASS` — своя сеть **2.4 ГГц**;
2. `MQTT_BROKER` — LAN-IP компьютера с docker (`ipconfig` → IPv4), **не** `localhost`;
3. `MQTT_USER` / `MQTT_PASS` — не `guest` (его пускают только с localhost);
4. на DevKit залит урок 22 (или 21) и он в сети;
5. `docker compose up -d` + `dotnet run` в `ArduinoEducation` — если хочешь ещё и
   историю в БД. Для самого катания бэкенд не обязателен: нужен только брокер.

```bash
pio run -e lesson26_fpv_robot -t upload

```

## Что проверить

1. **Колёса вывесить над столом.** Первый `forward` — с поднятыми колёсами.
2. В мониторе камеры: `[MQTT] -> commands/esp32/drive = forward`.
   В мониторе робота: `[MQTT] <- commands/esp32/drive = forward`. Если первое есть,
   а второго нет — робот не подключён к брокеру или у него другой `MQTT_BROKER`.
3. Отпусти кнопку — уедет `stop`; ничего не нажимай 1 секунду — у робота сработает
   failsafe.
4. Наклони робота круче 45° — на FPV-странице появится красная строка, робот
   перестанет реагировать на движение.
5. Клавиатура: W/A/S/D и стрелки, пробел = стоп.
6. С телефона: открой ту же страницу, кнопки работают на touch (`pointerdown`).
7. Замерь задержку: помаши рукой перед камерой, глядя на экран. Поток здесь стартует
   с **QVGA** — на этой плате стоит сенсор GC2145 без аппаратного JPEG, и каждый кадр
   жмёт процессор через `frame2jpg()` (см. уроки [23](lesson23_cam_snapshot.md) и
   [24](lesson24_cam_stream.md)). Для FPV это осознанный размен: лучше мелкая, но
   свежая картинка, чем красивая и запоздавшая. Поднимешь до VGA в `initCamera` —
   сразу увидишь, как растёт задержка.

## Питание на машинке

Две платы + четыре мотора — это уже энергетика, а не электроника:

- моторы (VM драйвера) — от батарей напрямую, **никогда** от 5V/3V3 платы;
- ESP32-S3-CAM — от своего 5 В (у тебя в схеме это MP1584EN), а не от пина DevKit:
  просадка от старта моторов уронит камеру в брауноут;
- общий GND у всего: батареи, драйвер, DevKit, камера;
- электролит 470–1000 µF по 5 В рядом с камерой сильно помогает.

Симптом «камера ресетится ровно в момент, когда машинка стартует» = питание, а не код.

## Вариант B: всё на одной плате (без DevKit)

На ESP32-S3 это уже реально: свободных линий 7–10 против «почти нуля» у AI-Thinker.
Раскладка под TB6612FNG из свободных пинов HW-679:

| Сигнал TB6612FNG | GPIO | Замечание |
|---|---|---|
| AIN1 / AIN2 | 1 / 2 | левый мотор, направление |
| PWMA | 14 | ШИМ левого |
| BIN1 / BIN2 | 3 / 21 | правый мотор, направление |
| PWMB | 47 | ШИМ правого |
| STBY | 3V3 | как в уроке 21 — всегда включён |
| MPU6050 SDA / SCL | 38 / 39 | если не нужен microSD (это его линии) |

Осталось свободным: 48 (и 40, если не занят SD). То есть tilt guard из урока 22 тут
**сохраняется** — это главное отличие от AI-Thinker, где датчик было некуда девать.

Три обязательные оговорки:

1. **ШИМ мимо LEDC-каналов камеры.** Камера держит `LEDC_CHANNEL_0` + `LEDC_TIMER_0`
   под XCLK, а в ядре 2.x `ledcSetup(ch, …)` привязывает канал к таймеру `ch/2`.
   Значит для моторов бери каналы 4 и 5 (таймер 2), подсветку оставь на 7 (таймер 3),
   а каналы 0/1 не трогай вообще. `analogWrite()` из урока 21 здесь не годится —
   он сам выбирает канал, и есть риск наступить на камерин.
2. **Проверь 47/48 «охотой за LED»** (`lesson_check_cam`): на части плат один из них
   разведён на подсветку, и мотор будет «мигать» вместе с ней.
3. **19/20 и 43/44 не занимать** — это нативный USB и UART0. Заберёшь их, и прошивка
   с монитором превратятся в квест.

Что при этом теряется: код урока 26 придётся дописать — вместо `mqtt.publish` в
`commands/esp32/drive` вызывать `applyCommand()` напрямую (моторы-то свои), а из урока
22 перенести MPU, failsafe и tilt guard. Это уже не «камерный» урок, а сборка нового
робота, поэтому в Этапе 6 по умолчанию вариант A.

## Встроить поток в React-дашборд (необязательный шаг)

Одним тегом, CORS для `<img>` не нужен:

```tsx
<img src={`http://${import.meta.env.VITE_CAM_IP}:81/stream`} alt="FPV" />
```

Тогда в дашборде рядом окажутся видео, стрелки управления, 3D-модель наклона и
график — то есть всё, что мы собирали с Этапа 2. Расширять CORS на бэкенде для
этого **не нужно**: браузер тянет картинку напрямую с камеры.
